# 엔진 능력 패리티 감사 (2026-07-24)

> 출처: 6개 엔진 패밀리 × 16개 능력 차원 코드베이스 감사(13 에이전트) + 제안 갭에 대한 적대적 실현성 검증.
> **중요: '적대 검증 교정' 절을 반드시 먼저 읽을 것.** 아래 갭 제안 중 상당수는 검증에서 원인 진단이 틀렸거나 작업량이 상향 조정됐다.

## 판정

Mostly yes. The honest split is roughly: about 15 percent of the missing depth is genuinely impossible, about 10 percent is achievable only as an equivalent operator outcome through a different mechanism, and the remaining 75 percent is work we simply have not done, over data sources that already exist and in most cases are already reachable by a collector or connector we shipped. TRUE PARITY (same dimension, same shape of answer) is achievable for: Aurora MySQL versus Aurora PostgreSQL on plan analysis, index advice, fragmentation, unused index and setting misconfiguration, because the inputs are already in the cache; RDS for MySQL on essentially everything except Performance Insights breadth, because the hard parts (in-VPC TLS transport, the Data-API-shape adapter, cache-table compatibility, approval-gated writes) are done and what remains is re-pointing Aurora-shaped calls at describe*db_instances / describe_db_parameters and deleting a blanket simulation:False; and anomaly detection, capacity ETA, query regression and findings surfacing for every family, since those are metric-shaped and the machinery is already engine-neutral. EQUIVALENT OUTCOME VIA A DIFFERENT MECHANISM is the right target for: SQL Server plan and index analysis (SHOWPLAN_XML and dm_db_missing_index*\* instead of PG EXPLAIN JSON and a regex parser, which is a better answer, not a worse one), ElastiCache expensive-operation analysis (SLOWLOG plus INFO commandstats instead of pg_stat_statements), DynamoDB hot-access-pattern analysis (Contributor Insights plus the per-GSI and per-operation series we already hold instead of top-N query text), and structure tracking for the three non-relational families (collection/index inventory, table-structure blobs, keyspace counts instead of DDL history). GENUINELY IMPOSSIBLE, and we should say so rather than paper over it: EXPLAIN, engine parameters and version upgrades for DynamoDB; index recommendation for ElastiCache; DDL-impact simulation for any schemaless family; VACUUM/bloat/XID/extension checks for MySQL; Aurora cluster-topology operations for standalone RDS instances; and Performance Insights breadth for rds_instance, which is an AWS ceiling we have live-verified. One framing point that matters more than any single gap: the deepest family is not uniformly deep either. Aurora PostgreSQL emits 20 finding check_types per cycle against Aurora MySQL's 10 inside the same family, and 2 of the 63 advertised gateway tools are dead for every engine because schema_snapshots has no writer. Parity work therefore starts inside the flagship family, not at the edges.

## 정직한 표기 문구

DBOps supports six engines on one shared spine (collection, cache, findings, approval-gated change, and a single conversational agent), with depth matched to what each engine actually exposes: Aurora PostgreSQL is the deepest surface, Aurora MySQL and RDS for MySQL add engine-internal deep reads and approval-gated writes, and RDS for SQL Server, DocumentDB, DynamoDB and ElastiCache each get native telemetry, engine-specific advisory findings, dashboards and guarded writes. We do not claim Aurora's query-tuning depth on the key-value and document engines because those engines do not expose it; where the mechanism differs (missing-index DMVs on SQL Server, SLOWLOG and commandstats on Redis, capacity and access-pattern telemetry on DynamoDB) the roadmap targets the same operator outcome through the engine's own native surface.

## 깊이 차이의 원인 분류

### [inherent_na]

A minority of dimensions cannot exist for an engine because the engine has no such concept. These are correctly refused today and should stay refused, roughly 15 of the 96 family-dimension cells.

- DynamoDB has no query planner and PartiQL on DynamoDB has no EXPLAIN, so D4 has no artifact to read; likewise no engine parameters (D12) and no engine version to upgrade (D14).
- ElastiCache Redis/Valkey/Memcached expose no secondary indexes (no RediSearch modules on ElastiCache), so D5 index recommendation cannot exist.
- DDL-impact simulation is meaningless for DynamoDB, DocumentDB and ElastiCache: no schema, no DDL, no lock model.
- Aurora MySQL cannot report txid_age, vacuum_overdue or extension_missing (no visibility-map freeze, no autovacuum, no CREATE EXTENSION); mysql_innodb_status.py:35-39 documents that Aurora also has no LSN/checkpoint section because storage is distributed with no local redo.
- Standalone RDS instances have no ACU, no reader fleet and no cluster endpoint, so modify_scaling, add/remove_reader_instance, custom endpoints and prewarm_reader are correctly gated off for rds_instance.
- cost_check.\_check_storage_rightsize is a deliberate no-op for Aurora: storage auto-scales and bills per GB used, so there is no shrink-the-disk advice to give.

### [engine_equivalent]

The largest and most interesting class: the operator need is identical but the native mechanism differs, and in several cases the engine's own mechanism is BETTER than the Aurora-shaped heuristic we ship. We mostly did not consume these, and in two cases we run the PostgreSQL heuristic anyway and emit wrong output.

- SQL Server index advice: sys.dm_db_missing_index_details + \_groups + \_group_stats returns equality/inequality/included columns with avg_user_impact straight from the optimizer, strictly better than regex-parsing query text. We instead run the PG-flavored parser, which returns nothing at all because mssql_query_stats never populates shared_blks_read.
- SQL Server plan analysis: plan_handle is already in sys.dm_exec_query_stats which we poll every 5 minutes; dm_exec_query_plan, dm_exec_text_query_plan, SET SHOWPLAN_XML and Query Store all supply a plan. Only our parser is PG-JSON shaped.
- MySQL (Aurora and RDS): EXPLAIN FORMAT=JSON exists, and sys.schema_unused_indexes / schema_redundant_indexes / performance_schema.table_io_waits_summary_by_index_usage supply the unused-index signal. mysql_table_stats already collects the index-usage rows and already maps DATA_FREE into n_dead_tup, so fragmentation and unused-index findings are threshold checks on data already in the cache.
- DynamoDB 'top queries' maps to Contributor Insights MostAccessedKeys / MostThrottledKeys, plus the per-operation latency and per-GSI consumed rows we already store (a most-expensive-operation and unused-GSI ranking needs no new AWS call).
- ElastiCache 'top queries' maps to SLOWLOG plus INFO commandstats/latencystats (calls, usec_per_call per command), the Redis analogue of pg_stat_statements. elasticache_live_read already opens the connection and reads SLOWLOG but never commandstats, and persists nothing.
- Schema tracking: DocumentDB has listCollections + list_indexes + $collStats, DynamoDB has the describe_table blob we already serialize every cycle and overwrite, ElastiCache has INFO keyspace + MEMORY STATS keys.count. Schemaless does not mean structure-free.
- max_connections for SQL Server is sys.configurations 'user connections' (0 meaning the 32767 default), which is why the engine-agnostic connection-exhaustion ETA is permanently silent for that engine.

### [aws_platform_limit]

Genuinely not ours. Small class, two items that matter.

- Performance Insights for rds*instance is capped at db.load.avg alone (pi_collector.py:19-23, live-verified 2026-07-22): SQL Server PI publishes no os.* and no PG-shaped db.\_ counters, and one unknown metric fails the whole batched GetResourceMetrics call. Honest nuance: for RDS MySQL several os.\* counters DO exist, so the shared narrow list is partly our choice, not AWS's.
- BufferCacheHitRatio is an Aurora-only CloudWatch metric with no RDS-instance equivalent, which is why param_buffer_cache_hit cannot fire from CloudWatch for rds_instance (the InnoDB buffer pool hit rate we scrape from SHOW ENGINE INNODB STATUS is the substitute and is simply not wired to that check).
- ElastiCache, DynamoDB and DocumentDB have no Performance Insights at all, so there is no AAS/wait-event surface of the Aurora kind for them.

### [customer_config]

Data exists on the engine but only if the customer enables it. We handle this well in one place (DocumentDB profiler: detect it off, emit a finding, offer an approval-gated flip) and badly in the most important place (performance_schema).

- RDS MySQL 8.x default parameter groups ship performance_schema=0 while Aurora MySQL ships it ON. The entire rds_direct_collector deep-read tier (query_stats, table_stats, blocking_locks, activity) is therefore silently EMPTY on a stock instance, and nothing detects or reports it. SELECT @@performance_schema is one query on a connection we already hold.
- SQL Server: Query Store must be enabled per database for durable per-plan runtime stats, and DMV reads need VIEW SERVER STATE granted to the dbops login.
- Slow-query capture for PG/MySQL needs log_min_duration_statement or slow_query_log plus the CloudWatch Logs export. pg_health_checks.py:50 already recommends the setting while nothing ingests the resulting log lines.
- DynamoDB Contributor Insights is per-table opt-in with its own cost; the DocumentDB profiler and its CloudWatch profiler log export are per-cluster parameters.
- Per-cluster cost breakdown needs cost allocation tags activated, which api/cost already states in its response note.

### [real_gap]

STRUCTURAL CAUSE 1, Aurora-shaped plumbing that was never re-pointed. The platform grew Aurora-first, so the transport and the control-plane calls assume a cluster. The result is not a clean refusal but a misleading or confidently wrong answer.

- cache_client.execute_on_target returns an empty QueryResult unless the registry row has cluster_arn AND secret_arn, which rds_instance rows never carry. explain_plan therefore returns 'cluster not registered or unreachable' on a cluster that IS registered, for both RDS MySQL and SQL Server, even though execute_sql already routes those rows through mysql_direct / mssql_direct.
- modify_parameter calls rds.describe_db_clusters and is NOT in \_ENGINE_GATED_TOOLS, so on any RDS instance, DocumentDB or ElastiCache cluster it returns lookup_failed with a raw AWS exception string in the response (also a str(e) leak against project rules).
- forecast_capacity.\_resolve_limit hardcodes Aurora's 128 TiB ceiling and is ungated, so on an RDS instance it forecasts against a limit roughly 1000x the real AllocatedStorage and will essentially never warn, while the correct math already exists in capacity_forecast.py and the correct limit already sits in cluster_meta.resource_details.
- recommend_index is ungated and emits CREATE INDEX CONCURRENTLY, invalid DDL on Aurora MySQL and RDS MySQL and invalid T-SQL on SQL Server. Wrong-but-confident output is worse than a refusal.
- The performance and incident MCP handlers have zero engine gates, so get_top_queries / get_slow_queries / detect_regressions return an empty list instead of unsupported_engine for DynamoDB and ElastiCache: a false empty state instead of a redirect.

### [real_gap]

STRUCTURAL CAUSE 2, blanket capability switches and dispatch-table omissions. Depth is often withheld by a single boolean or a missing dict key, not by an absent capability. These are the cheapest gaps in the audit.

- CAPABILITIES[RDS_INSTANCE]['simulation'] = False is one switch that kills upgrade, DDL-impact and parameter simulation together. All three have their data source in-repo already: describe_db_engine_versions/ValidUpgradeTarget is engine-agnostic and already called, and table_stats is already populated for the family.
- \_CAPACITY_METRICS_BY_FAMILY has relational/documentdb/dynamodb keys only (verified), so /capacity-forecast returns not_applicable for ElastiCache and rds_instance even though the input series and the REGR_SLOPE machinery are family-neutral.
- collect_pg_baselines (engine-agnostic, reads only metric_snapshots) is called from the relational and rds_instance branches only, so DocumentDB, DynamoDB and ElastiCache anomaly detection is permanently stuck in low-confidence flat mean/stddev mode instead of seasonal median/IQR.
- diagnose_root_cause.py:418 and correlate_signals.py:14 hardcode metric_type IN ('aas','cpu','db_connections') (verified). DocumentDB writes cpu_utilization, not 'cpu', so an RCA for DocumentDB, DynamoDB or ElastiCache ranks zero metric signals, while \_collect_elasticache_signals proves the per-family collector pattern works.
- maintenance-health-panel CHECK*LABELS has no entry for any of the 7 elasticache*\* check_types and no TABS_ELASTICACHE, so the family falls through to the MySQL tab strip and its own cost finding does not appear under 'Cost'.

### [real_gap]

STRUCTURAL CAUSE 3, read paths that exist but are never persisted, so nothing downstream can trend, alert or regress on them. The precedent for the fix is in the repo (docdb_mongo_collector persists Mongo diagnosis on a 5-minute schedule).

- elasticache_live_read reads INFO, SLOWLOG, CLIENT LIST and MEMORY STATS over a real in-VPC connection with redis/pymemcache bundled, and writes nothing: no table, no finding, no trend, no UI caller. That single omission is what makes ElastiCache D3 and D9 empty.
- docdb_mongo_collector reads system.profile every 5 minutes and throws away everything except a count, a max and a top-5 namespace tally, discarding the per-op millis/keysExamined/docsExamined/planSummary that would populate query_stats and make the engine-agnostic regression collector work unchanged.
- query_plan_history is written only when a human or the agent calls explain_plan, never on a schedule, so plan flips between invocations are invisible and query_regression cannot distinguish a plan flip from data growth.

### [real_gap]

STRUCTURAL CAUSE 4, one platform feature was never built at all, and it degrades every engine. The single largest cross-family hole.

- schema_snapshots has zero producers: no CREATE TABLE in schema.sql or any of schema_v2..v25, no INSERT anywhere, and the data-pipeline/schema_tracker/ directory promised in .kiro/steering/structure.md does not exist. Verified by grep: only readers (schema_history.py:7, schema_diff.py:108/125, diagnose_root_cause.py:234) plus tests that encode 'relation schema_snapshots does not exist' as the EXPECTED condition.
- Blast radius: get_schema_diff and get_schema_history are 2 permanently dead tools inflating the advertised 63-tool count, and diagnose_root_cause drops its DDL signal into skipped_sources on EVERY RCA for EVERY engine, losing the most common real root cause of a query-latency incident.
- The api/dashboard \_schema_changes proxy (table_stats n_live_tup deltas) is table-granularity and row-count driven, so an added column, a new index, a widened type or a rename are invisible, and a real DROP is indistinguishable from a table falling out of the top-100-by-size ranking.

### [real_gap]

STRUCTURAL CAUSE 5, wiring and surfacing bugs that make already-built depth invisible or unreachable in production. The most embarrassing class, because the hard work is already done.

- Nothing in the product can write mongo_secret_arn or mongo_write_secret_arn: \_register_docdb does not set them and PATCH /clusters/{id}/meta whitelists only purpose, service_tags, db_name, db_secret_arn, db_write_secret_arn (verified in api/clusters/handler.py:978-993). So the entire DocumentDB in-VPC deep-read collector skips every cluster and both approval-gated Mongo writes return 'no write credentials configured', unless someone hand-edits DynamoDB.
- api/dashboard _health_findings uses one global MAX(snapshot_time) for every family except rds_instance, which got the per-check_type window fix with a comment about exactly this hazard. DocumentDB is the other family with TWO independent finding writers on separate schedules with disjoint check_type sets, so its docdb\_\_ and docdb*mongo*_ sets alternate out of view. incident/maintenance_findings.py has the same bug.
- search_logs defaults to /aws/rds/cluster/{cluster_id}/error and the agent Lambda's Logs IAM is scoped to /aws/rds/cluster/\* only, so /aws/rds/instance/{id}/slowquery and /aws/docdb/{cluster}/profiler|audit are IAM-denied even with an explicit override.
- No aws.elasticache EventBridge subscription exists (data_stack subscribes aws.rds plus CloudWatch alarm state changes only), so the ElastiCache audit tab is structurally empty and event-driven auto-RCA never fires for a cache incident.
- Collected but unrendered: innodb*checkpoint_age_mb (the one InnoDB signal RDS MySQL has and Aurora does not) is missing from MYSQL_METRICS; DocumentDB's 7 mongo*\* metric types are charted nowhere; IndexRecsPanel and RedundantIndexesPanel are relational-only although \_index_recommendations works for rds_instance and a complete MySQL redundant-index SQL branch already exists in the handler.
- Latent defects found in passing: proactive_monitor filters only NOT jsonb_exists(dimensions,'instance'), so DynamoDB per-GSI and per-operation rows pollute table-level anomaly baselines; HealthScore reads the last batch-timeseries point without filtering the gsi dimension; HealthScore has no rds_instance signal set and falls through to SIGNALS_RELATIONAL, leaving replica_lag_ms, deadlocks and buffer_cache_hit permanently blank.

## 엔진별 능력 매트릭스

### Aurora relational (MySQL + PostgreSQL) — engine_family RELATIONAL, sql_via=data_api

This family really is the deepest baseline: it is the only family with all 6 dashboard tabs (TABS_BY_FAMILY.relational = overview/perf/advisory/internals/config/audit), the only one where CAPABILITIES grants sql+simulation+custom_endpoint+prewarm+scale_instance simultaneously, and no performance/incident MCP tool refuses it (performance/handler.py and incident/handler.py contain zero engine gates; only operations/simulation gate, and always in relational's favour except the rds_instance/NoSQL positive caps). But "deepest" hides two real holes. (1) Schema/DDL tracking is fabricated depth: `get_schema_diff` and `get_schema_history` both SELECT from `schema_snapshots`, a table that has no CREATE TABLE in schema.sql or any of schema_v2..v25 and no collector anywhere (the `data-pipeline/schema_tracker/` directory promised in structure.md does not exist on disk) — so 2 of the 63 gateway tools are permanently dead and diagnose_root_cause silently drops its DDL signal into `skipped_sources` on every RCA. (2) Aurora MySQL is a second-class citizen inside its own family: PG emits ~20 distinct check_types per ETL cycle vs MySQL's ~10 (no txid_age/dead_tuples/vacuum_overdue/table_bloat/index_unused/extension_missing/setting_misconfigured because pg_health_checks.py is gated on `"postgresql" in engine`), `explain_plan` has no engine branch at all and builds PG-only `EXPLAIN (FORMAT JSON, VERBOSE)` which is a syntax error on MySQL, `recommend_index` emits `CREATE INDEX CONCURRENTLY` (invalid MySQL DDL), and PlanTree renders "Non-PostgreSQL plan — tree view not yet implemented". Depth parity across engines is clearly achievable — most of what is missing is a collector plus a table, over the exact same RDS Data API path already used 12 times per cycle — but the honest read is that even the baseline family is only at parity with itself on the PostgreSQL side.

### RDS for MySQL (non-Aurora, rds_instance family)

RDS for MySQL is the deepest non-Aurora family in the codebase and is genuinely close to Aurora-MySQL parity on the read/observe axis: a dedicated in-VPC direct-TCP Lambda (data-pipeline/rds_direct_collector/, 5-min schedule, fail-closed TLS) runs the five Aurora-MySQL collectors VERBATIM through a Data-API-shape adapter (mysql_adapter.MySQLDataApiAdapter), so query_stats, table_stats, blocking_locks, cluster_settings, long_running_queries and five InnoDB gauges all land in the same cache tables the engine-agnostic tools and panels already consume. CloudWatch (11 instance-dimensioned metrics), anomaly detection, query-regression, capacity/disk-exhaustion ETA (with an rds_instance-EXCLUSIVE free_storage_bytes branch Aurora cannot use), 8 finding check_types across two Lambdas with a purpose-built per-check_type read query, three fail-closed approval-gated instance writes with verified 3-place sync, direct-TCP execute_sql for reads and approved writes, and a Price-List-accurate right-sizing simulator (the one capability rds_instance has that Aurora lacks) are all real and live. The honest weaknesses are concentrated and almost entirely real_gap, not platform limits: (1) EXPLAIN is completely absent and returns a misleading 'not registered' because execute_on_target is Data-API-only, even though the direct-TCP shim execute_sql uses is right there and MySQL EXPLAIN FORMAT=JSON is fully available; (2) recommend_index is UNGATED and emits PostgreSQL-only 'CREATE INDEX CONCURRENTLY' DDL that cannot run on MySQL, which is worse than refusing; (3) 'simulation: False' is a blanket switch that also kills upgrade, DDL-impact and parameter simulation, all three of which have their data source already in-repo (describe_db_engine_versions/ValidUpgradeTarget is engine-agnostic and already called; table_stats is already populated); (4) parameter TUNING has no working path at all — modify_parameter calls describe_db_clusters and dies with 'lookup_failed', the spec'd modify_rds_instance_params was never built, and the fitness advice text actively tells this family not to tune innodb_buffer_pool_size on the false premise that Aurora manages it; (5) forecast_capacity hardcodes Aurora's 128 TiB ceiling and is ungated, so it will essentially never warn; (6) no config tab, so 18 collected global variables and all backup state are invisible; (7) the whole deep-read tier silently depends on performance_schema, which RDS MySQL 8.x ships OFF by default while Aurora ships it ON, and nothing detects or reports the empty result. Two gaps are legitimately not ours: Performance Insights is reduced to db.load.avg alone (aws_platform_limit, documented and live-verified) and BufferCacheHitRatio has no RDS-instance equivalent. ### RDS for SQL Server (engine_family rds_instance, engines sqlserver-ee/se/ex/web)

RDS for SQL Server is a real, live-verified engine in DBOps, not a stub, but its depth is a thin vertical slice rather than parity. What genuinely works end to end: instance-dimensioned CloudWatch collection (11 metrics), a direct-TCP pytds deep-read path with enforced TLS reading four DMVs (dm_exec_query_stats, dm_exec_sessions, dm_exec_requests, dm_os_wait_stats), per-query top/slow analysis, interval-delta query-regression detection (which required a deliberate GROUP BY query_hash fix because dm_exec_query_stats is per-cached-plan), seasonal anomaly detection, disk-exhaustion ETA findings purpose-built for standalone RDS, a complete and license-aware right-sizing cost simulation on the real Price List API, and four fully guarded approval-gated write paths including T-SQL execution with a SQL-Server-specific fail-closed master-write rejection. What is missing splits cleanly. Only ONE dimension is a true AWS ceiling: Performance Insights gives this engine just db.load.avg, live-verified, because a single unknown metric fails the whole batched call. Only the Aurora-topology simulations (ACU scaling, reader scale-out, cluster endpoints, pg_prewarm) are inherently N/A for a standalone instance. Everything else is real_gap or engine_equivalent, and in most cases the data source is already sitting behind a connection we open every five minutes: execution-plan analysis (plan_handle is already in the DMV we query; SHOWPLAN_XML, dm_exec_query_plan and Query Store all available), index recommendation (dm_db_missing_index_details is the engine's own optimizer-grade advisor, strictly better than the PG-flavored regex parser we ship, which in practice returns nothing at all for this family because shared_blks_read is never populated), engine-internal breadth (dm_os_performance_counters alone would fill the one-card internals tab, the dead HealthScore deadlocks signal, and a first findings collector), table sizes (dm_db_partition_stats; TableSizesPanel renders but is structurally always empty), parameter tuning and fitness (sys.configurations for reads, and modify_db_parameter_group is the same boto3 family we already call), and upgrade simulation (describe_db_engine_versions ValidUpgradeTarget exists; only our estimator is Aurora-shaped). Two defects deserve calling out beyond the depth question: modify_parameter is ungated and hard-wired to describe_db_clusters, so on a SQL Server instance the agent gets a lookup_failed with a raw AWS exception string leaked into the response, and explain_plan returns a misleading "cluster not registered or unreachable" because execute_on_target silently requires the cluster_arn/secret_arn that rds_instance rows never carry. Finally, D16 schema tracking is dead for every engine, not just this one: schema_snapshots has zero producers and no DDL anywhere, and the schema_tracker directory in the steering docs does not exist. Verdict on the audit's actual question: depth parity for SQL Server is achievable and mostly cheap, because the hard part (in-VPC TLS connectivity, a Data-API-shape adapter, cache-table shape compatibility, approval-gated writes) is already built and the remaining work is overwhelmingly new SQL against DMVs on that existing connection plus family entries in three or four dispatch tables.

### Amazon DocumentDB (engine_family DOCUMENTDB)

DocumentDB is the only non-relational family with a real engine-internal deep-read path (an in-VPC pymongo Lambda running a read-only serverStatus/currentOp/profile allowlist), and it has a respectable CloudWatch + findings + dashboard shell: 16 CW metric types every 5 min, 8 proactive check_types, a purpose-built overview panel, a DocDB-aware health score, live topology/backup/engine-config REST paths, and 2 fail-closed approval-gated Mongo writes. Below that shell the depth is thin and, more importantly, two of the best pieces are effectively dark in production: nothing in the product can write `mongo_secret_arn` / `mongo_write_secret_arn` onto a registry row (`_register_docdb` does not set them and `PATCH /clusters/{id}/meta` only whitelists purpose/service_tags/db_name/db_secret_arn/db_write_secret_arn), so the deep-read collector skips every cluster and both write tools return `unsupported_engine: no write credentials configured` unless someone hand-edits DynamoDB; and the mongo collector only reads profiling from the hardcoded `admin` database, where application slow ops never land. Additionally the dashboard's global MAX(snapshot_time) findings query hides half the findings, because DocumentDB (uniquely among families other than rds_instance, which got the fix) has TWO independent finding writers on separate 5-min schedules with disjoint check_type sets. Genuinely absent: any per-query stats, explain/plan analysis, index recommendation, query-regression, capacity/exhaustion finding, parameter fitness, cluster-level writes, and any simulation whatsoever, plus DocDB spend is invisible in the Cost view. Almost none of this is inherent to the engine: DocumentDB exposes explain(), $indexStats, system.profile with keysExamined/docsExamined/planSummary, a CloudWatch profiler log export, a small readable cluster parameter set, ValidUpgradeTarget, and full instance pricing. Depth parity is achievable here; the gaps are unbuilt work (plus one credential-wiring omission), not platform limits.

### Amazon DynamoDB

DynamoDB is the second-deepest non-relational family after ElastiCache, but its depth is concentrated almost entirely in one layer: CloudWatch capacity/throttle telemetry and the six rules built on top of it. What is genuinely strong: a capacity-mode-aware collector with per-GSI and per-operation dimensioning at 1-minute granularity (5-minute ETL cadence), six DynamoDB-specific findings with correct capacity-unit math (per-minute Sum consumed divided by the timestamp-aligned per-second provisioned value via LATERAL join, sustained-window gating, read/write side correlation for hot-partition detection), three fail-closed approval-gated writes with payload-hash-bound single-use approvals and a TOCTOU re-read, a Price-List-backed Provisioned-vs-On-Demand cost simulator with an honest degradation contract, and a four-tab dashboard (overview / AI advisory / config / audit) that correctly withholds perf and internals. Everything above the metric layer is thin. The whole query-level column (D3/D4/D5/D9) is empty, and only D4 is truly inherent: DynamoDB Contributor Insights (MostAccessedKeys / MostThrottledKeys) is the named native mechanism for top-consumer and key-level analysis and it appears nowhere in the codebase, while unused-GSI and over-projection detection plus per-operation latency regression are computable from data already sitting in metric_snapshots and cluster_meta today. RCA is the sharpest real gap: diagnose_root_cause and correlate_signals both hardcode metric_type IN ('aas','cpu','db_connections'), so a throttling incident on a DDB table produces zero ranked signals even though an \_collect_elasticache_signals-shaped collector would need no new data source. Two self-contradictions deserve fixing: our findings tell the DBA to enable autoscaling while the platform can neither read nor set Application Auto Scaling targets, and modify_dynamodb_capacity refuses any table with a GSI, i.e. exactly the tables that trip ddb_gsi_throttling. Two latent defects found: proactive_monitor's dimension filter excludes only 'instance', so per-GSI rows are mixed into DDB anomaly baselines, and HealthScore reads the last batch-timeseries point without filtering the gsi dimension. Overall verdict for the parity question: depth parity is achievable for this family, because the honest classification of the missing pieces is overwhelmingly real_gap (unbuilt wiring over data we already hold or over Contributor Insights / Cost Explorer / CloudTrail APIs that exist today) rather than aws_platform_limit; only EXPLAIN, engine parameters and version upgrade are inherently meaningless here.

## 하지 말 것 (본질적 불가 / YAGNI)

- DynamoDB plan analysis or any EXPLAIN-shaped feature: inherent. No planner, PartiQL on DynamoDB has no EXPLAIN, and the only plan-shaped decision (Query versus Scan, which GSI) is made by the application. The nearest substitute, per-request ConsumedCapacity, is application-side instrumentation we cannot collect for the customer.
- ElastiCache index recommendation: inherent. No secondary indexes on ElastiCache Redis/Valkey (no RediSearch modules) and none in Memcached by construction.
- DDL-impact simulation for DynamoDB, DocumentDB and ElastiCache: inherent. No schema, no DDL, no lock model to estimate.
- MySQL txid_age, vacuum_overdue and extension_missing checks: inherent. InnoDB has no visibility-map freeze or autovacuum and MySQL uses plugins rather than CREATE EXTENSION. Do not synthesise a lookalike finding just to make the check_type count match PostgreSQL.
- Aurora storage-shrink cost advice: inherent. Aurora auto-scales the volume and bills per GB used, so cost_check.\_check_storage_rightsize staying a no-op for relational is correct, not a gap.
- Serverless v2 ACU cost findings for standalone RDS and DocumentDB, and ACU / reader / custom-endpoint / prewarm operations for rds_instance: inherent. No ACU, no reader fleet, no cluster endpoint on a standalone instance.
- innodb_checkpoint_age_mb for Aurora MySQL: platform shape. Aurora has no local redo log, so the LSN and checkpoint sections do not exist in SHOW ENGINE INNODB STATUS. It is an RDS-MySQL-exclusive signal and should be presented that way rather than backfilled (do render it for rds_instance, which is a one-line UI fix).
- Chasing the full 12-metric Performance Insights set for rds_instance: AWS ceiling, live-verified. One unknown metric fails the whole batched GetResourceMetrics call and SQL Server publishes no os.\* counters. A separate PI metric list for RDS MySQL alone is a small optional follow-up, not a parity project.
- DynamoDB Contributor Insights: defer. Per-table opt-in with its own cost, and no customer has asked. Most of the value it would deliver (unused GSI, over-projection, per-operation latency regression) is computable today from resource_details.gsi and the per-GSI and per-operation rows already in metric_snapshots. Build the free half first and reach for Contributor Insights only when key-level hot-partition attribution is actually requested.
- SQL Server showplan XML parser: defer. Large effort, single family, and the engines whose customers actually tune query text are PG and MySQL. Revisit after MySQL EXPLAIN ships and a SQL Server customer asks; the missing-index DMVs deliver most of the tuning value at a fraction of the cost.
- Per-node ElastiCache metric dimensioning and ElastiCache Serverless registration: YAGNI. Hot-shard detection matters only for cluster-mode-enabled multi-shard deployments and no serverless cache is registered today. Both are list-and-dimension edits when a customer brings one.
- A DocumentDB cluster-write suite (reboot, snapshot, failover, instance class, replica add/remove): defer. Largest write-parity gap on paper, but nothing in our diagnosis chain drives those actions except a single cost_oversized finding, and the console covers them. Build the write when a finding recommends it, which is the pattern that made the ElastiCache and rds_instance write sets defensible.
- Reserved-node and reserved-capacity purchase modelling for ElastiCache and DynamoDB: marginal. Cost Explorer already surfaces Savings Plan and reservation recommendations, and cost_check already pulls the real CE recommendation for the RDS families.
- A generic cross-engine plan or index abstraction layer: YAGNI and actively harmful. PG plan JSON, MySQL query_block and SQL Server showplan XML are three genuinely different shapes. Three small parsers behind one dispatch stay readable; one unified plan model will not.

## 규칙

클러스터 레벨 집계는 **strict 형태만** 쓴다.

```sql
AND (dimensions IS NULL OR dimensions::text = '{}')
```

`NOT jsonb_exists(dimensions, 'instance')`(weak 형태)는 **불충분하다.** PI 대기이벤트
행과 GSI 행에는 `instance` 키가 없어 그대로 통과한다. E-0에서 리뷰어 둘이 엇갈린
지점이며 strict가 맞다.

정본: `mcp-servers/mcp_servers/shared/metric_filters.py`
(`CLUSTER_LEVEL_ONLY`, 세부 행을 의도적으로 남기는 리더용 `EXCLUDE_PER_INSTANCE`).

**verbatim 복제**하고, `tests/unit/test_metric_filters.py`가 두 파일의 동일성을 단정한다.
나머지 패키지(`api/simulation`, `data-pipeline/*`)는 람다 asset이 각각 분리돼 있어
